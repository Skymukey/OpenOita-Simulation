# V2 整体重构与验收记录（2026年10月8日）

本记录描述 V2 核心重构当前的代码架构、资源迁移方式和验收边界。结果按证据目录和验证方法分列；历史过程数据与当前正式证据分开记录，不把历史结果写成最终通过。

## 当前架构

V2 的正式入口是 `WorldHost` → `MaterialWorldFactory` → `WorldSourceLoaderV2` → `MaterialWorld`。正式运行时使用 `Assets/Scripts/OpenOitaWorld/V2/` 下的网格、规则、事件、结构、物理、查询和显示实现。旧 `SimulationWorld`/`WorldRuntime` 路径已从正式 V2 装配中移除；`MaterialWorld` 不调用旧运行核心。旧模块文件和旧报告仍可作为历史资料，不能作为 V2 的运行路径或验收证据。

V2 的材料网格是稀疏 32×32 Native 页。画布只保留页目录，缺页读取为空且不分配；`MaterialPagePool` 以固定 16 KiB 页复用 slab，主网格和动态体网格可以共享页池。显示页仍按 128×128 组织。热状态直接保存在页内，燃料、寿命和传播时间等冷状态由 `TimedComponentStore` 持有。

规则移动按区块四色调度：颜色为 `(chunkX & 1) | ((chunkY & 1) << 1)`，同一 Tick 按固定颜色顺序处理。每个任务只写本页及一格 halo；同色页之间相隔 64 格，写入区域不重叠。格子的处理 Tick 和移动标记防止同一 Tick 跨颜色重复移动。水和蒸汽枚举活动位图，燃烧按到期事件调度；稳定材料可以休眠，结构、接触和局部唤醒仍可重新激活相关页。

事件时间使用绝对 Tick。`TimedComponentStore` 的四级 256 桶时间轮保存绝对到期 Tick，删除事件先脱链，槽位复用时递增 generation。蒸汽到期、燃烧传播和燃尽按绝对时间处理；删除会撤销链表事件，复用槽位增加代次，Reset重建时间轮。移动不会重置冷状态。

湿接触由 `ChangedWetJob` Burst 任务处理局部脏水邻格，只提交实际燃烧组件的灭火请求；跨 31/32 页的重复接水仍按组件/句柄守恒燃料，不重复扣减。该路径保留边界邻格唤醒，不把局部扫描扩大成全图扫描。

结构连通由页内 component root 和页边界图组成。`MaterialConnectivity` 的局部重建只收集 dirty tile 邻域涉及的旧连通组，重建后只从旧闭包和新增 root 计算 new group 差量；首次全量构建才进行全图分量计数。边界 key 维护 slot 索引和 root→边索引，局部删除不再扫描全边界列表。动态体另有固定 32 格桶的 `NativeBodySpatialIndex`，查询先取候选再做局部精确几何。

物理覆盖、湿接触和显示提交都以变化页/变化体为边界。动态体位姿变化只替换旧覆盖与新覆盖的差集，覆盖计数和被覆盖页按差量更新；`Published` 对外提供变化块、体事件、版本和租约，读取不重新比较两份全世界快照。GPU 显示使用变化页和已提交版本，倒计时变化不等同于颜色变化。

每个 `BodyRuntime` 持久拥有其 `MaterialConnectivity`。初次建立结构目录允许全量重建，之后只重建 topology dirty tile 邻域；跨页仍可保持一个连通分量，`ComponentCount` 在确认全图只有一个连通组后可提前结束。四方向边界连接及连接组检查已修复；PlayMode回归覆盖8193格支撑删除后分成两个4096格体，并验证材料守恒。

## 配置与地图迁移

V2 运行 Loader 只接受三个 `schemaVersion=2` 文件，`world_config.json` 不接受 `chunkSize`，运行页大小固定为 32。CPU 内存预算拒绝已关闭：V2 Loader 不因 256 MiB 或 512 MiB 估算拒绝创建或推进；材料数、动态体、形状、变化数、命令和接触等数量上限仍生效。显式传入有限预算的旧 Loader/测试仍可验证预算逻辑。普通 V2 运行不采样托管 heap/峰值内存；最终 `AcceptanceAllocationCpuFinal` 使用独立 Native scoped probe，13 个非 fracture 场景的 10000 个采样行均为 0 bytes，Native 正向/空范围控制为 4128/0，且 supported=true。这证明受测 Tick 范围内无记录分配，不代表 heap 峰值或 M09 的 256 MiB 内存目标。

V1 到 V2 必须显式迁移。`WorldV2SourceConverter` 先严格校验合法 V1 三文件，再改写三个 schema 版本并移除 `world.chunkSize`，最后用 V2 Loader 再校验。Editor 菜单“OpenOita/迁移选中关卡资产到 V2”使用 Unity `AssetDatabase` 生成唯一的 `*-V2.asset`，原始关卡资产不覆盖。`V2ProjectUpgrade` 同样以 Unity API 另存 V2 场景和地图；当前 BasicSandbox 的 V2 验证资源由 Unity API 生成到独立资产，原始场景和关卡保持保留。

## 正式 Host 试玩 smoke

正式试玩包位于 `Builds/V2Playable/`；启动入口是包内根目录的 `Builds/V2Playable/StartOpenOita.cmd`，不是仓库根目录下的同名脚本。该入口默认传入 `-force-d3d11 -force-gfx-direct`。需要验证正式场景显示时，在包目录执行：

```powershell
StartOpenOita.cmd -openoita-v2-validate-render `
  -openoita-v2-validate-render-output="D:\Project\Unity Project\OpenOita-Simulation\logs\V2-Implementation\PlayableSmoke\formal-host.png"
```

验证模式使用现有正式场景的 Host 世界和原相机；由于隐藏 swapchain 可能不自动产生可读帧，它显式调用 `SingleCameraRequest` 写入验证 RenderTexture，再读回 PNG。当前证据为 `tick=1000`、`uploaded=1000`、`tiles=20`、`camera=Main Camera`，日志同时确认管线为 `UniversalRP`，后续 Tick 1250/1500 的显示版本为 1249/1499。该 smoke 证明正式 Host 世界能创建、推进并产生真实显示输出，不替代 CPU/GC/GPU 矩阵。

`OpenOitaGpuTimer.dll` 的 `Flush` 只存在于 benchmark-only GPU 计时边界；正式 Host smoke 和普通运行不对每帧调用它，也不能把 benchmark/offscreen 计时解释为普通 Host 每帧成本。资源 provenance 位于 [`v2-provenance.json`](../../logs/V2-Implementation/Provenance/v2-provenance.json) 与 [`v2-provenance.csv`](../../logs/V2-Implementation/Provenance/v2-provenance.csv)，本次记录 209/209 文件存在、missing=0；该 provenance 只做 SHA256/文件元数据核对，`heapSampling=false`。

分配证据与 CPU 计时分开。`AcceptanceAllocationCpuFinal` 已通过 13 个非 fracture 场景的严格全行零分配检查，且正向/空范围控制为 4128/0；它没有进行 heap 峰值采样。CPU 预算关闭不等于 M09 原内存目标 256 MiB 已满足，内存结论仍需独立的峰值/预算证据。

## GPU 与显示

GPU 计时器只用于 benchmark。`OpenOitaGpuTimer.dll` 在 D3D11 下对真实 URP 相机帧写入原生 timestamp；benchmark-only 的 `End` 会在结束 event query 后调用 `ID3D11DeviceContext::Flush`，将命令提交到 GPU，但不会等待 GPU 完成，轮询仍使用 `D3D11_ASYNC_GETDATA_DONOTFLUSH`。Microsoft 文档说明 Flush 是异步的，但不必要的调用会产生显著开销，参见 [`ID3D11DeviceContext::Flush`](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush)。因此该 Flush 只改变 benchmark 的提交边界，不能拿来推断普通 Host 的 CPU/GPU 成本，也不能把旧 deferred-submission 结果和新结果混用；metadata 必须记录 `nativeGpuEndQueryAsyncFlush=true`。最终验证脚本默认核验 `Logs/V2-Implementation/AcceptanceDisplayVerified/` 和 `Logs/V2-Implementation/AcceptanceAllocationDisplayVerified/`，并要求完整 FinalBlit 范围、camera tail 尾点、Direct 线程模式日志和直接 GPU/显示 p95。GPU p95 统一按 raw CSV 的 nearest-rank（最近秩）计算，metadata GPU p95 仅作对照；`AcceptanceDisplayDirectFinal` 与 `AllocationDisplayDirectFinal` 是 boot 配置无效时的失败 pilot，不能混入最终证据。无 DLL、非 D3D11 或没有真实相机帧时，显示 GPU 字段应记录为 `NA`/unsupported。

## 剩余边界

四组验收矩阵与正式 Host smoke 均已完成并由各自证据核验；仍不包含托管 heap 峰值采样，也不把 scoped Tick/显示准备零分配推论为 heap 峰值或 256 MiB 目标已满足。CPU timing 证据绑定 V2TimingFrozen Player 与当前 harness；正式 Host smoke 只增加 CLI 验证日志和显式相机请求，不改变普通 Host/Tick 语义。benchmark-only 的 GPU `Flush` 不会进入普通 Host 每帧路径。旧失败 pilot、旧范围、旧线程模式和旧 PNG 均不纳入最终证据。
