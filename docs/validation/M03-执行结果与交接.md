## 实测环境与结果

Unity 6000.3.11f1，WindowsEditor；Intel Core i7-14700HX，16091MiB RAM，Windows11 10.0.26200。使用已连接的 `OpenOita@9d1fd0f10939c3a7` 编辑器；环境及内存探针见 [环境记录](m03-environment.json)。Editor/Editor PlayMode 均不是 Windows Player，未测 IL2CPP。

- 最终 EditMode：**212通过、0失败、1未测/忽略**，总数213，耗时5.033468秒；其中既有166项全部通过，M03 46项通过、1项未测。job=`5c48ad6ae81141eeabb643241aeb4daf`；[逐项原始结果](m03-editmode-result.json)。
- PlayMode：既有2项通过、0失败、0跳过，耗时0.4527591秒；job=`5f007e9bcdb941f9b7dff057d79b7c62`；[逐项原始结果](m03-playmode-result.json)。没有新增动态规则 PlayMode 测试，这两项仅回归 M00消费者/M02状态生命周期。
- 最终编译及 Console：error/warning均0。`git diff --check`通过；新增资产带Unity生成的meta。编辑器API探针在运行前后返回 None、enabled=false，最终已退出PlayMode；另检查落盘配置发现Test Runner将选项写为1，已仅将该项恢复到本轮开始的0，保留原启用值1。自动生成的SceneTemplateSettings.json按这一个明确文件路径删除，其余配置未改。
- 未测项是 `M03_A_WarmedRuleAllocationRequiresWorkingPositiveControl`。当前 `.NET GC.GetAllocatedBytesForCurrentThread` 对显式8192字节数组的正对照仍返回0；同步 `GC.Alloc` 正对照仅200字节，未获得可靠逐调用分配证据。因此测试主动忽略，**不把早期“0字节”读数认定为达标**。规则路径采用预分配数组/容器、无逐格对象、无运行时扩容；实际 GC/完整 Step 性能仍须 M09 在 Player/Profiler 测量。
- 独立构造65536格容量规则表，GC回收后 `Profiler.GetMonoUsedSizeLong` 的构造保留差为141615104字节，保守预留218107904字节。这只是当前Editor一次构造的内存差，不是模拟CPU峰值、分配率或256MiB全系统验收。

## 复验入口

在该Unity版本的Test Runner运行 `OpenOita.Tests.EditMode`；只看M03时按 `OpenOita.Tests.EditMode.Rules` 筛选。PlayMode运行既有 `OpenOita.Tests.PlayMode`。本次实际使用Unity MCP `refresh_unity(scope=all,mode=force,compile=request)`、Console检查、`run_tests(mode=EditMode,assembly_names=[OpenOita.Tests.EditMode])` 及对应PlayMode，再由 `get_test_job` 取得保存的原始结果。

关闭该项目编辑器后也可按AGENTS在仓库根目录运行：

```powershell
$unityEditor = 'D:\Unity\Editors\6000.3.11f1\Editor\Unity.exe'
& $unityEditor -batchmode -projectPath (Get-Location).Path -runTests -testPlatform EditMode -testResults Logs/m03-editmode-results.xml -logFile Logs/m03-editmode.log
```

该batchmode命令是复验方式，本轮没有另起第二个编辑器执行它。原始JSON保留每项通过/失败/未测信息，分配正对照失效时明确保留未测结果。
