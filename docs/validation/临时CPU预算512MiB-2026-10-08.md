## 同日内存组成与空间索引诊断补充

经用户请求分析，在暂停的Editor PlayMode中通过内存内C#和反射构建隔离临时世界，复用正式Create的初态、结构/物理Apply和EnsureRules阶段，读取首次空间索引预检前预算。临时世界均在finally中Dispose；最后恢复停止Play。未修改运行源码、地图布局或512 MiB上限。

状态105.54 MiB中，MaxMaterialCells×640占40 MiB、MaxChangesPerTick×192占12 MiB、实际材料37251×1088占38.65 MiB、22区块占11.69 MiB、提交快照占2.56 MiB，其余为头部、材料表、体和形状预留。不是各项实际内存测量；特别是按上限预留项和流体暂存估算不意味着已创建对应数量记录。

`WorldRuntime.Refresh`先计算`ReservedCpuBytes + (reuse ? 0 : WorldOccupancyIndex.EstimateCpuBytes(State.MaterialCells))`。新增预留函数直接为`4096 + N×8192`；首次构建不能复用，所以37251格得到305164288字节。本次573.14 MiB指这个公式的结果，不是内存峰值。

为了解容器本身规模，在另一份隔离世界中直接调用索引Refresh观察首次构建；这个诊断调用未经过WorldRuntime的总预算拒绝分支，不改变正式Host行为。实际得到37251条目、47181桶、555380个桶内列表容量槽位、1个动态体。建成索引的`ReservedCpuBytes`为74793808字节（71.33 MiB），公式为`4096 + 1024E + 400B + 64C + 32K + 256Q + 128D + 32S`；E/B/C/D为历史条目/桶/候选/体数量高水位，K/Q为候选及接触列表Capacity，S为所有池化桶列表的累计容量。本次C、K、Q均为0。条目预算36.38 MiB、桶预算18.00 MiB、槽位预算16.95 MiB。

单次同步Editor探针以`GC.GetTotalMemory(true)`在对象构造前后采样，并用`GC.KeepAlive`保证目标在后样本仍存活：37251容量规则表托管保留增量59498496字节（56.74 MiB）；隔离索引构建托管保留增量24334336字节（23.21 MiB）。这只是该次Editor托管堆差值，可能受后台分配/GC计量影响，不涵盖完整模拟、Unity原生/物理/GPU内存，也不是持续运行峰值或GC性能验收。规则表预检131.16 MiB、索引建成容量预算71.33 MiB、新建候选预算291.03 MiB是三种不同口径，不能混用。

索引按材料格几何建立SortedDictionary条目和空间桶；桶按网格固体、动态固体、其它材料保存三个列表。Bounds在格边界加epsilon，轴对齐格也会覆盖相邻桶，通常约3×3，因此会重复保存格位置；列表扩容Capacity又大于成员数。Invalidate清空内容并将桶归池，保留列表/哈希容器容量；SortedDictionary清空后的旧节点可被GC，保留预算仍按历史高水位计。重建前仍另加完整8192N，因而可能重复覆盖可复用的存储。暂存流体计入State.MaterialCells，却不进入OccupiedCells索引，也会使候选估算偏保守。

结论：当前启动被拒绝直接由保守空间候选公式触发。后续优化宜先明确常驻/新增/扩容峰值的各自口径，按目标容器容量估算增量并验证；再按规则实际参与集缩小缓冲，减少桶重复存储。不能直接把上述堆差值当成安全上限，或未经负载验证就下调常数。
