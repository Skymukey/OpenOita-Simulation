# V2 显示验证说明

日期：2026-10-08  
环境边界：Unity 6000.3.11f1、URP 17.3；范围为 `OpenOita.V2.MaterialWorldDisplay`、`OpenOita.V2.Render.IncrementalWorldRenderer`、V2 URP 2D RenderGraph 路径及其 PlayMode 显示测试。

## 实现边界

V2 显示读取已提交的 `MaterialWorld` 版本。相机真正进入 `WorldRenderFeatureV2.RecordRenderGraph` 时，`MaterialWorldDisplay.PrepareForCamera` 才按相机范围准备显示缓存；模拟 Tick 不因相机隐藏而创建逐 Tick 的托管上传队列。每个逻辑材料格仍对应一个像素，渲染缓存按 128×128 格 tile 分片，多个 tile 共用 `Texture2DArray` page（每页 128 个 layer）。纹素以 `R32_UInt` 保存 packed material id、燃烧标记和 fuel bin；Compute pass 只把最终的脏像素写入 page，材质 shader 通过 65536 色调色板取色。动态体只更新 pose 缓冲，不因位姿变化重建像素纹理或逐格 GameObject。

普通静态 tile 使用一个程序化六顶点 quad。火焰也没有 CPU 火焰 Mesh 或逐格对象：有火 page 才提交火焰 pass，每个实例为一个 tile 的 6 顶点 quad，shader 从本 tile、下方一格和下方两格读取 burning 标记并生成形状、波动和透明度。当前诊断值 `EstimatedFireVertexCount` 表示实际提交的火焰顶点估算（有火 page 为 `6 × 128` 个实例顶点），不是燃烧格数量；无火 page 不提交火焰 pass。火焰 quad 已向上延伸到 130/128 tile 高度，边界行为由专门的 URP 读回测试覆盖。

显示屏障中的像素更新按 `(page layer, x, y)` 去重，隐藏期间反复写同一像素只保留最后值；`ClearPixelLayer` 使用该 layer 的 dirty 槽清理，不扫描其他 layer 的 pending 列表。NativeList、GraphicsBuffer、pose 数组只在初始化或明确的显示屏障扩容，steady frame 不在 `WritePixel` 中增长。没有变化的帧仍添加 draw pass，以便相机继续绘制缓存；此时应没有新的像素或 pose 上传。

当前增量路径由主线程按可见范围收集 32×32 `MaterialTile` 操作，每个 page 在 `FlushFrame` 中运行一次串行 Burst job。job 直接处理该 page 的 `PackedPixels`、`DirtySlots`、`PendingUpdates`、free slots、燃烧位图和层计数，读取持久材料定义与冷记录；它不创建逐格 GameObject、火焰 Mesh 或托管像素对象。`FlushFrame` 会先对所有 page 做只读容量预检，再允许任一 page 消费 Visual/缓存；容量拒绝因此保留 dirty、燃烧和缓存状态，关闭当前显示帧，扩容后可重新进入屏障重试。`IJob.Run` 会复制 job struct，因此 job 内可变总燃烧数通过持久 `BatchBurningTotal` NativeArray 回传，错误和层状态变化也通过 NativeArray 回传；`HasBurning`、实例数据和可观测上传计数只在成功 job 后同步。批处理容量不足会显式失败，不能把失败帧当作有效显示结果。

## 可记录指标

`MaterialWorldDisplay` 暴露 `LastPreparationMs`、`LastPreparationAllocated` 和 `LastPreparationAllocationSupported`，它们只包围相机显示准备。普通 Host 路径不主动调用线程级 GC 计数 API；显式 benchmark 才初始化 `ScopedAllocationProbe`，并以正向分配校准后选择可用计数器。分配计数器不可用、嵌套或溢出时 `display_prepare_allocated_bytes` 保持 `NA`，不能把未测写成 0。`IncrementalWorldRenderer` 暴露 `LastDrawSubmissionMs`、`LastFramePixelUpdates`、`LastFramePoseUpdates`、`PendingPixelUpdateCount`、`PendingBodyPoseUpdateCount`、`EstimatedFireVertexCount` 和 `ActiveTileCount`。首次初始化、Reset、缓存扩容和新相机范围建立属于冷路径，不能与 steady frame 的零变化结果混报。

`LastFramePixelUpdates` 和 `PendingPixelUpdateCount` 统计 page 内最终去重后的上传槽，不是批处理操作数或访问过的逻辑格数；`LastFramePoseUpdates` 同样是最终 pose 槽范围内的变化数。`EstimatedFireVertexCount` 是有火 page 的 tile-instance 提交估算，不能用来推断燃烧格数量。只有 `FlushFrame` 成功完成批处理后，这些计数器及 `HasBurning` 才可作为该帧显示结果使用。

基准入口是 `-openoita-v2-display-benchmark`。默认使用 `Resources/OpenOita/BenchmarkCurrent`、单个 1920×1080 URP 相机和 RenderTexture，每个相机帧最多推进一个已提交 Tick，默认预热 1000 Tick、采样 10000 Tick；可通过同名 `-warmup=`、`-samples=` 和 `-output=` 参数覆盖。CSV 当前字段为：

`scenario,phase,tick,generation,step_ok,render_frame,step_ms,display_prepare_ms,display_prepare_allocated_bytes,draw_submit_ms,gpu_frame_ms,estimated_fire_vertices,active_tiles,pending_pixel_updates,pending_pose_updates`

`render_frame=0` 时显示 CPU/GPU 列写 `NA`。`FrameTimingManager` 返回的正值只有在具有非零 frame/submit identity 时才进入去重窗口；timestamp 为 0 的记录直接舍弃，不能补猜 Tick 归属。其结果仍不写入当前 Tick 的 `gpu_frame_ms`，因为 Unity 返回窗口可能跨 Tick 延迟。

Windows D3D11 Player 可选用 `OpenOitaGpuTimer.dll` 的独立 GPU scope：benchmark-only `NativeGpuTimingFeature` 在隔离 Renderer2D 的 URP 2D RenderGraph 中注册 `BeforeRendering` 起点；end pass 在 benchmark 的 camera-tail 模式下不挂在 `AfterRenderingPostProcessing`，而是在 `SingleCameraRequest` 返回后用持久 CommandBuffer 追加 plugin end/poll 事件，因此覆盖 RenderGraph 后续的 PixelPerfect、FinalPost、FinalBlit、Overlay UI、Debug/Gizmo 尾段（若该相机启用）。URP 2D 的 `GetInjectionPoint2D` 仍将起点映射到 `BeforeRendering`；RenderGraph 将整图记录进同一 CommandBuffer 后再提交，camera-tail command 在 request 返回后排队，不等待 GPU，也不调用额外 `ScriptableRenderContext.Submit`。基准相机使用 LDR `ARGB32` 外部 RenderTexture、MSAA 1、默认关闭普通后处理；`SingleCameraRequest` 对 2D、mip 0 目标直接把目标 RT 作为 `camera.targetTexture`，URP 仍以 `resolveFinalTarget=true` 完成相机，外部目标会走 renderer 的 FinalBlit。原生层在 render thread 用 `D3D11_QUERY_TIMESTAMP_DISJOINT` 和 timestamp query；结束 event query 后仅在 benchmark-only DLL 中调用一次 `ID3D11DeviceContext::Flush`，再以 `D3D11_ASYNC_GETDATA_DONOTFLUSH` 异步轮询，metadata 必须记录 `nativeGpuEndQueryAsyncFlush=true`。Flush 只提交命令、不等待 GPU，并带有额外开销，不能等同普通 Host 的 CPU/GPU 成本。metadata 的 `nativeGpuMetric=elapsed_device_timestamps_including_queue_idle` 明确 `gpu_ms` 是设备 timestamp 的 elapsed interval，`nativeGpuMayIncludeQueueIdleOrSubmissionGap=true` 明确它可能包含队列 idle、驱动供给或提交间隙。GPU scope 不包含 `MaterialWorldDisplay` CPU 准备或 CPU `SubmitRenderRequest` 的 managed 区间，但 camera-tail 可能包含渲染线程/驱动供给间隙，不能直接等同纯 shader busy。scope 使用单调 `scope_id`；采样窗口保存 warmup cutoff，晚到的 warmup scope 被过滤。原始结果写入 `<csv>.gpu.csv`，列含 `scope_id,gpu_ms,render_thread_event_ms,flags,phase`；`render_thread_event_ms` 是 begin/end plugin callback 的 render-thread 墙钟区间，用来识别 GPU timestamp 尖峰是否伴随命令回放/驱动阻塞，不替代 GPU ms。metadata 记录 `gpuSource`、scope 端点和覆盖项、CPU prepare/submit 是否包含（均应为 false）、camera-tail end 次数、支持状态、drop、invalid、scope 数和分位数；也记录实际 `GraphicsSettings.currentRenderPipeline`、相机 renderer/data、活动 benchmark feature、RenderGraph begin pass 执行次数和 `nextScopeId`，用于区分 feature 未进入 Player、tail 未排队与原生 query 未完成。构建 helper 会通过 Unity API 临时覆盖全部 QualitySettings level 的管线引用，保存各 level 的 asset path，构建后按 path 重新加载并恢复当前级别，避免 clone 资产被卸载后留下 null 引用。`renderRequestSubmitTotalMs`/`renderRequestSubmitFrames` 覆盖所有 warmup、sample、drain 的 `SubmitRenderRequest` CPU 调用，独立于 GPU scope；`render_request_submit_ms` 是包含 `PrepareForCamera` 的外层 CPU 区间，不能再加 `display_prepare_ms`。`phase=sample` 与 `phase=drain` 分开记录。旧 callback 试跑 raw 数据仅作历史链路记录，不进入最终 GPU busy 判定。插件不可用、非 D3D11、benchmark RendererGraph 未装配或没有完成 scope 时保持 `NA`。

## 验证状态与边界

最终真实 URP PlayMode 回归为 41/41 通过，原始 XML 为 `Logs/V2-Implementation/playmode-v2-final-render.xml`。新增 `SingleCameraRequest` 远端坐标回归覆盖相机中心不在原点时的目标 RT/像素定位；Player 路径已显式绑定相机 VP 矩阵，旧的仅原点放大 PNG 已废弃，不能作为当前显示证据。Build scope 现在保存各 QualitySettings 的管线 asset path，构建后通过 Unity API 重新加载并恢复，避免 clone 资产卸载后配置变成 null。测试等待 `RenderPipelineManager.endCameraRendering`，不以 `Camera.Render()` 或手工 CPU cache 检查冒充 URP 像素验证。

最终 GPU timing 目录 `AcceptanceDisplayVerified` 与 allocation-display 目录 `AcceptanceAllocationDisplayVerified` 均已完成 3×10000 矩阵，并由 `VerifyV2Acceptance.ps1 -VerifyGpu` 通过。GPU timing raw p95 为 `current40k=0.143360 ms`、`mixed1m-concentrated=0.295936 ms`、`mixed1m-bodies64-rotating=0.505856 ms`；outer request+GPU 的保守 p95 为 0.411336/2.574296/2.904544 ms。所有场景 PNG 均来自新的完整矩阵相机输出，metadata 记录 `nativeGpuEndQueryAsyncFlush=true`。GPU p95 按 raw CSV 最近秩计算，并通过 Direct 线程日志、FinalBlit scope、camera tail、drop/invalid 和完整场景集合检查；每个 scope `[1033,11033)` 与 tick 1001–11000 的 sample 行按 `scope_id-start` 映射，三组 timing 映射错误均为 0。

CPU 与 Native scoped allocation 两组矩阵、GPU timing 与 allocation-display 两组矩阵均已通过各自 verifier。CPU 模拟 benchmark 与显示/GPU benchmark 是两套证据，不能互相替代；硬件、驱动、URP batch、目标分辨率及可见 tile 数量都会改变结果。`render_request_submit_ms` 是包住 `MaterialWorldDisplay.PrepareForCamera` 与 RenderGraph 记录/提交的外层 CPU 区间；metadata 的 `renderRequestSubmitScopeRelation` 明确这一嵌套关系，验收汇总不得把它与 `display_prepare_ms` 相加。保守逐帧成本只计算 outer request+GPU elapsed，前者用于完整单相机请求成本，后者用于显示准备子阶段。

## 正式 Host 显示 smoke

正式试玩包使用 `Builds/V2Playable/StartOpenOita.cmd`，入口位于包内根目录。以 `-openoita-v2-validate-render` 启动时，`HostedRenderValidation` 绑定原正式场景中的 `WorldHost`、`Main Camera` 和 UniversalRP，显式提交一次 `SingleCameraRequest` 到 1920×1080 RenderTexture；它不创建 benchmark fixture。正式 smoke 记录 `tick=1000`、`uploaded=1000`、`tiles=20`、`camera=Main Camera`，并输出真实 Host 截图 [`formal-host.png`](../../logs/V2-Implementation/PlayableSmoke/formal-host.png) 与原始日志 [`formal-host-render-smoke.log`](../../logs/V2-Implementation/PlayableSmoke/formal-host-render-smoke.log)。

该模式用于证明正式 Host 世界确实创建、推进并在真实相机上产生显示；隐藏 swapchain 的显式请求只属于验证辅助。`OpenOitaGpuTimer.dll` 的 `Flush` 仅在 benchmark-only GPU scope 中使用，普通 Host 运行不会每帧调用它，因此 smoke 截图和 benchmark/offscreen 证据不能解释为普通 Host 每帧 Flush 成本。

## 复核清单

1. 在 Editor 中确认 `Resources/OpenOita/V2Rendering.asset` 已绑定 Compute、WorldPage 和 WorldFire 资源，并确认 Renderer2D 已装配 `WorldRenderFeatureV2`。
2. 在可实际绘制 GameView 的 Editor 环境运行 V2 PlayMode 测试，先重跑材料/空白/Remove/Reset/无 Tick，再重跑普通火焰和 128 格边界上方火焰读回。
3. 在目标 Player 上使用 benchmark 启动参数，保留 CSV、`.metadata.json`、`.gpu.csv` 和 PNG；分别检查三个场景的 warmup/sample 数、真实 render/drain 帧数、`render_frame`、显示准备分配、像素/pose 上传计数、native scope cutoff/drop/invalid 和 GPU `NA` 比例。
4. 稳态无变化帧应保持 `LastFramePixelUpdates=0`、`LastFramePoseUpdates=0`，同时仍有 draw pass；第一次注册 tile、Reset 或可见范围扩张允许出现初始化上传与显示屏障扩容。

## 风险与限制

当前风险边界是 scope 可能包含 render-thread 提交或队列同步等待而不能等同纯 shader/GPU busy 时间、真实 GPU/驱动差异，以及 `FrameTimingManager` 本身的采样开销。41/41 PlayMode、正式 Host smoke 与四组 benchmark 矩阵已通过，但 GPU scope 仍应按其 metadata 边界解释。容量异常会显式失败；失败帧及其之后尚未重新建立的缓存状态不能纳入功能或性能统计，需在下一显示屏障完成容量预留后重跑。FrameTiming timestamp 为 0 的记录不会被伪造为有效样本。大地图的模拟卡顿仍应按物理/规则阶段单独定位；不能因为显示路径采用增量 GPU 上传，就把既有水出口搜索或 Editor 侧开销解释成纯 GPU 瓶颈。Native scoped allocation 和显示准备零分配不包含 heap 峰值监测。

## 静态源码依据

- `Assets/Scripts/OpenOitaWorld/V2/MaterialWorldDisplay.cs`：相机显示屏障、可见 tile 计算、视觉 dirty 消费、动态体 pose 和代次 Reset。
- `Assets/Scripts/OpenOitaWorld/Render/V2/IncrementalWorldRenderer.cs`：page/layer 缓存、像素去重、Compute 更新、pose buffer、RenderGraph draw、相机图层过滤和诊断计数器。
- `Assets/Scripts/OpenOitaWorld/Render/V2/WorldRenderFeatureV2.cs`：将 renderer 接入 URP `RecordRenderGraph`。
- `Assets/Shaders/V2/WorldPage.shader`、`Assets/Shaders/V2/WorldFire.shader`：逐像素材质采样、fuel brightness、燃烧邻格采样及火焰几何/裁剪。
- `Assets/Scripts/OpenOitaWorld/V2/Validation/V2DisplayBenchmarkRunner.cs`：1920×1080 单相机、场景 fixture、warmup/sample/drain、PNG、metadata 和 raw scope 采集入口。
- `Assets/Scripts/OpenOitaWorld/V2/Validation/NativeGpuCameraTimer.cs`、`Assets/Scripts/OpenOitaWorld/V2/Validation/NativeGpuTimingFeature.cs`、`Tools/Performance/NativeGpuTimer.cpp`：D3D11 独立 RenderGraph scope 计时链路；`Assets/Scripts/OpenOitaWorld/Editor/V2BenchmarkRenderingSetup.cs`：以 Unity API 复制隔离 URP/Renderer2D 并装配 benchmark-only feature；`Tools/Performance/BuildNativeGpuTimer.ps1`：本机 DLL 构建入口。
