# V2 运行与基准说明

日期：2026年10月8日

## 正式运行

V2 正式场景通过 `WorldHost` 创建 `MaterialWorldFactory`，加载 `StreamingAssets/OpenOitaV2/` 下的 `materials.json`、`world_config.json` 和 `scene.json`。三文件必须是 `schemaVersion=2`；V2 Loader 不接受 `world.chunkSize`，运行时页大小固定为 32。进入 PlayMode 后才创建正式世界，Editor 非 PlayMode 只提供配置、编辑和迁移能力。

V2 的正式 Tick 顺序为：命令预检与接收、移动前湿接触、水/蒸汽四色局部规则、灭火与延迟点燃、燃烧事件、结构增量、物理子步与覆盖/湿接触、暂存恢复、发布版本和变化页。湿接触使用 Burst `ChangedWetJob` 处理局部 dirty 邻格，只提交实际燃烧组件的灭火；跨 31/32 页的重复接水按组件和句柄保持燃料守恒。外部读取使用版本租约；下一 Tick 后旧租约失效。CPU 内存预算拒绝当前关闭，不能据此推断实际内存峰值已达标；材料、体、形状、命令和变化数量限制仍有效。

正式 Host smoke 已在 `Builds/V2Playable/` 包内完成。包内根目录的 `StartOpenOita.cmd` 是试玩启动入口；它默认传入 `-force-d3d11 -force-gfx-direct`，不要把仓库根目录或 benchmark Player 当作试玩入口。需要对正式场景做一次可复核的显示验证时，在包目录执行：

```powershell
StartOpenOita.cmd -openoita-v2-validate-render `
  -openoita-v2-validate-render-output="D:\Project\Unity Project\OpenOita-Simulation\logs\V2-Implementation\PlayableSmoke\formal-host.png"
```

该 CLI 使用实际 `WorldHost`、`Main Camera`、UniversalRP 和正式地图，不创建 benchmark fixture；隐藏 swapchain 场景下会显式提交一次 `SingleCameraRequest` 以读回验证 RT。当前证据记录 `tick=1000, uploaded=1000, tiles=20, camera=Main Camera`，日志见 [`formal-host-render-smoke.log`](../logs/V2-Implementation/PlayableSmoke/formal-host-render-smoke.log)，截图见 [`formal-host.png`](../logs/V2-Implementation/PlayableSmoke/formal-host.png)。这项 smoke 证明正式 Host 能创建、推进并产生真实显示输出；它不替代四组 benchmark，也不意味着普通 Host 每帧使用 GPU 计时器的 `Flush`。

## 地图和资源操作

V1 关卡迁移使用菜单 `OpenOita/迁移选中关卡资产到 V2`。菜单先严格校验 V1 三文件，再用 Unity `AssetDatabase.GenerateUniqueAssetPath` 和 `AssetDatabase.CreateAsset` 另存 `*-V2.asset`。它不覆盖原始地图资产，也不通过手写 `.meta`、场景或 prefab YAML 完成迁移。

当前 BasicSandbox 基准资产由 Editor/Unity API 另存为独立的 `Resources/OpenOita/BenchmarkCurrent.asset`，基准运行时读取该资产的真实尺寸和格子数。当前版本应为 960×640、33803 个非空格；若资源尺寸或格子数不符，benchmark 会拒绝启动。原始 BasicSandbox 关卡和场景仍保留。

执行 V2 显示资源和 Renderer2D 装配菜单后，验证场景可以使用 `Assets/Scenes/BasicSandboxV2.unity` 或独立 benchmark 场景。benchmark 场景中的 Camera 和 DirectionalLight 状态会写入 metadata；CPU 基准可关闭 Camera 以排除显示，显示基准必须明确记录实际启用状态。

## CPU benchmark

默认脚本是 `Tools/Performance/RunV2Benchmark.ps1`。它对每个场景启动独立 Player，默认 1000 Tick 预热、10000 Tick 采样；每个采样的完整 `world.Step()` 和 fixture 操作都计入对应字段。fracture 场景在墙钟开始前单独执行 Reset，并将 Reset 耗时写入 `reset_ms`；Reset 不计入该 Tick 的 `wall_tick_ms` 或 `total_ms`。移除支撑命令和 Wake 操作发生在 Tick 墙钟范围内。脚本只检查进程和日志是否完成，最终是否达标必须查看 CSV 和 metadata。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Tools\Performance\RunV2Benchmark.ps1 `
  -Player .\Builds\V2Validation\OpenOitaV2Benchmark.exe `
  -OutputDirectory .\Logs\V2-Implementation\FinalCpu
```

显示 benchmark 必须通过 `RunV2Benchmark.ps1 -Display` 启动；它向 Windows Player 传入 `-force-d3d11 -force-gfx-direct`。正式试玩入口是包内 `Builds/V2Playable/StartOpenOita.cmd`，二者用途不同。直接双击或无参数启动 Player 不能证明 Direct 线程模式，验证日志必须包含 `kGfxThreadingModeDirect`。最终显示矩阵使用 `AcceptanceDisplayVerified`，旧 `AcceptanceDisplayDirectFinal` 是 boot 配置无效时的失败 pilot。

最终验收完成后使用 `Tools/Performance/VerifyV2Acceptance.ps1` 生成 `AcceptanceSummary.json` 和易读 Markdown 表。脚本只调用 `SummarizeV2.ps1` 汇总 `AcceptanceCpu` 的 CPU 计时；`AcceptanceAllocationCpuFinal`、`AcceptanceDisplayVerified` 和 `AcceptanceAllocationDisplayVerified` 分别独立核验 Native 分配和 GPU/显示证据，分配验证运行耗时不会进入 CPU 分位数。缺少目录或 CSV 时不能判定为通过，必须补齐后复核；可用参数覆盖四个目录和输出路径。最终核验使用 `-VerifyGpu`。

只测指定场景时传入 `-Scenario`；不要用短样本替代默认矩阵。当前场景目录如下：

| 场景 | 负载定义 |
| --- | --- |
| `current40k` | 从 `BenchmarkCurrent.asset` 读取当前 BasicSandbox，960×640、33803 格，含完整物理。 |
| `water1m-concentrated` / `water100k-dispersed` | 2048×2048，总非空 1,000,000，其中约 100,000 个水活动腔；集中或分散布局。 |
| `steam1m-concentrated` / `steam100k-dispersed` | 同样总量和活动规模，材料为蒸汽。蒸汽集中/分散分别测。 |
| `burning1m-concentrated` / `burning100k-dispersed` | 总非空 1,000,000，其中 100,000 个长寿命燃烧木格，燃烧事件单独记录。 |
| `mixed1m-concentrated` / `mixed100k-dispersed` | 水、蒸汽和少量燃烧混合，保留约 100,000 个活动流体/燃烧材料。 |
| `bodies64-8192-rotating` / `bodies64-8192-sleeping` | 64 个体、每体 128 格、合计 8192 格；旋转和睡眠分开测。 |
| `mixed1m-bodies64-rotating` / `mixed1m-bodies64-sleeping` | 总非空严格 1,000,000：100,000 活动混合材料、891,808 固定填充、64×128 体内材料；旋转和睡眠分开测。 |
| `fracture8193-concentrated` | 集中结构破坏；Reset 在 Tick 墙钟开始前单独计入 `reset_ms`，不计入该 Tick 的 `wall_tick_ms` 或 `total_ms`；移除支撑命令和完整 Tick 计入采样范围。 |

百万格夹具使用固定材料填充保持总量，不能把固定填充删除后再称为百万格基准。`WithPhysics` 对这些验收场景为 true；64 体场景还要记录体数、旋转/睡眠数、body material cells 和 body events。

### 活动参数

活动夹具会修改运行表以保证 10000 个采样 Tick 内仍有可观察活动，这些参数不是默认材料值：

- 水 `moveIntervalTicks=1`，默认配置为 2。
- 蒸汽 `moveIntervalTicks=1`、`lifetimeTicks=1000000`，默认配置为 3/200。
- 木头 `fuelTicks=1000000`、`spreadIntervalTicks=10`，默认燃料为 250；传播间隔保持 10，不能改成 100000 来隐藏燃烧工作。

CSV metadata 必须保留 `waterInterval`、`steamInterval`、`steamLifetime`、`woodFuel`、`woodSpreadInterval`，并在报告中说明这是持续活动 fixture 参数，不能冒称默认值或默认 200/250 长跑结果。燃烧场景应同时记录 `burning_cells`/`Grid.BurningCount`，不能只用 `rule_attempts` 作为燃烧活动证明。

## 输出文件和字段

每个场景写出：

- `Logs/V2-Implementation/AcceptanceCpu/<scenario>-<timestamp>.csv`（当前最终 CPU 矩阵，14 个场景，每项 10000 个有效采样）
- `Logs/V2-Implementation/AcceptanceAllocationCpuFinal/<scenario>-<timestamp>.csv`（最终 Native 分配矩阵，13 个非 fracture 场景，已完成逐行验证）
- `Logs/V2-Implementation/AcceptanceDisplayVerified/`、`Logs/V2-Implementation/AcceptanceAllocationDisplayVerified/`（强制 Direct 线程模式的最终显示/GPU 目录，均为 3 个场景×10000 sample，已完成验证）
- `Logs/V2-Implementation/FinalCpu/`、`FinalMixed/`、`FinalFracture/` 是历史过程目录，不与 `AcceptanceCpu` 混用；最终结论必须绑定对应 CSV、metadata 和源码版本。
- 同名 `.csv.metadata.json`
- 同名 Player 日志

metadata 至少包括场景、预热/采样请求与完成数、`complete`、`invalidSamples`、Unity/操作系统/CPU/图形设备、`physics`、宽高、非空格数、活动格数、旋转/睡眠体数、`fracture`、fixture 参数、峰值 `peakTotalMs`/`peakWallMs` 和 `allocationMetric`。`invalidSamples` 或 `activity_valid=0` 的样本不能混入有效 p95/p99。`allocationMetric` 必须注明验证方法；最终 Native scoped probe 还必须记录 `allocationSupported`、正向/空范围控制和逐行分配状态，不能用 heap 推论替代。

CSV 的主要列为：

`tick`、`generation`、`total_ms`、`timer_ms`、`flow_ms`、`events_ms`、`structure_ms`、`physics_ms`、`fixture_ms`、`wall_tick_ms`、`reset_ms`、`peak_total_ms`、`peak_wall_ms`、`wake_cells`、`burning_cells`、`activity_valid`、`nonempty_cells`、`rule_attempts`、`moves`、`sleeping`、`tile_jobs`、`main_structure_cell_visits`、`main_structure_edge_visits`、`coverage_candidate_visits`、`wet_candidate_visits`、`body_count`、`rotating_body_count`、`sleeping_body_count`、`body_material_cells`、`body_events`、`changed_blocks`、`suspended_count`、`allocated_bytes_thread`、`gc0`、`gc1`、`gc2`。

`total_ms` 是世界内部完整 Tick 计时，`timer_ms` 只覆盖绝对事件时间轮推进及到期蒸汽处理；`flow_ms`、`events_ms`、`structure_ms` 和 `physics_ms` 是各阶段计时。`wall_tick_ms` 是包含 fixture 操作的外层墙钟；`fixture_ms` 和 fracture 的 `reset_ms` 要单列，不能把嵌套阶段简单相加。`allocated_bytes_thread` 由 `ScopedAllocationProbe` 提供，最终 Mono 数据的后端为 `native_mono_allocation_profiler`，CSV 写入在范围之外。旧 `FinalCpu`、`FinalMixed` 和 `DisplayPilot` 的字段 0 不具备当前分配验收效力；`AcceptanceAllocationCpuFinal` 的 13 个非 fracture 场景已通过 Native scoped probe：每个 CSV 10000 行全部为 `allocation_status=supported` 且 `allocated_bytes_thread=0`，metadata 的正向/空范围控制为 4128/0、`allocationSupported=true`。这只证明受测 Tick 范围无记录分配，不是堆峰值或进程内存采样，不能由此推断 heap。CPU 预算关闭也不代表 M09 原内存目标 256 MiB 已满足。

## 显示 benchmark

给脚本传 `-Display` 运行显示基准；默认只运行 current40k，或显式指定场景。显示 benchmark 使用 1920×1080 的真实相机帧，CPU 显示准备与 GPU 时间分别记录。`OpenOitaGpuTimer.dll` 只在 D3D11 benchmark 中启用；结束 event query 后执行 benchmark-only `Flush`，轮询使用 `D3D11_ASYNC_GETDATA_DONOTFLUSH`，不等待 GPU。该 Flush 有额外开销，不能代表普通 Host；metadata 必须记录 `nativeGpuEndQueryAsyncFlush=true`。非 D3D11、插件缺失或没有真实帧时记录 unsupported/NA。

## 结果判定

V2 规格中的目标是当前验收目标，不是自动通过条件：当前 BasicSandbox 40k 场景 p95≤4 ms、p99≤8 ms；百万格/十万活动目标 p95≤10 ms、p99≤16 ms；集中结构破坏峰值≤50 ms；稳态 Tick 和显示准备 `GC Alloc=0`；1920×1080 显示 p95≤4 ms。`AcceptanceAllocationCpuFinal` 已以 Native scoped probe 验证 13 个非 fracture 场景各 10000 行的 `allocated=0` 及 supported 控制；该结论不包含 heap 峰值，最终报告仍须绑定实际构建、机器、CSV、metadata 和验证方法。

当前 CPU 最终证据在 `Logs/V2-Implementation/AcceptanceCpu/`，14 个场景均完成 1000 预热/10000 采样：`current40k` p95/p99=0.1043/0.1327 ms，满足当前地图 p95≤4、p99≤8；其余场景按 `AcceptanceSummary.json` 核对百万/活动场景 p95≤10、p99≤16，`fracture8193-concentrated` 最大值 49.3075 ms，均满足。完整明细和检查状态见 `Logs/V2-Implementation/AcceptanceSummary.json` 与 `.md`。历史 `FinalCpu`、`FinalMixed` 只作过程比较，不能与最终矩阵混用。

GPU timing 与 allocation-display 也由 `VerifyV2Acceptance.ps1 -VerifyGpu` 完整核验通过。GPU timing raw CSV 的最近秩 p95（ms）为：`current40k` GPU/outer request/outer+GPU = 0.143360/0.282200/0.411336，`mixed1m-concentrated` = 0.295936/2.332600/2.574296，`mixed1m-bodies64-rotating` = 0.505856/2.406600/2.904544；`display_prepare_ms` 已包含在 outer request 内，保守和没有重复加入该嵌套阶段。每组 raw scope `[1033,11033)` 与对应 CSV sample 行按 `scope_id-start` 连续映射，三场景的 tick 映射错误为 0。`AcceptanceAllocationDisplayVerified` 三场景同为 10000 行，`display_prepare_allocated_bytes=0` 全行成立，metadata 正向/空范围控制为 4128/0 且 supported=true；其 instrumented 时序不参与 timing 组性能阈值。CPU timing 使用 V2TimingFrozen Player 与当前 harness；旧 FinalCpu/FinalMixed 仍仅作历史过程比较。

混合场景已改为按 `ordinal % 100` 构造并重新生成；修改前的 mixed CSV 不可作为当前混合负载验收证据。

旧 `FinalMixed` 长跑和旧 GPU threaded 矩阵均为过程对照；旧 GPU 记录有缺失 FinalBlit 范围、线程模式错误或 CPU 等待尖峰，不能作为最终显示结论。`AcceptanceDisplayDirectFinal` 与 `AllocationDisplayDirectFinal` 是 boot 配置无效时的失败 pilot；最终 GPU 目录 `AcceptanceDisplayVerified` 与 `AcceptanceAllocationDisplayVerified` 已完成并通过完整 verifier。GPU p95 统一按 raw GPU CSV 的 nearest-rank（最近秩）计算，metadata 内插 p95 只作对照，不参与通过判定；对应 `display-<scenario>.log` 必须包含 `kGfxThreadingModeDirect`，metadata 还必须有 `nativeGpuEndQueryAsyncFlush=true`。该 Flush 只在 benchmark-only 原生计时器中使用，异步提交、不等待 GPU，并有额外提交开销；普通 Host 不使用这条计时边界。详见 Microsoft [`ID3D11DeviceContext::Flush`](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush)。

Connectivity 已补齐四方向边界重建和 `ConnectionGroup` 一致性检查，连通分量根节点读取路径已使用 `HotReadMaterial` 避免无关 cold 状态展开。EditMode 63/63 与 PlayMode 41/41 的原始 XML 已记录；此前 incoming 边缺失使 fracture 旧 pilot 无效，不能把旧 pilot 的结构结果写入最终矩阵。CPU、Native allocation、GPU timing 和 allocation-display 四组最终目录均由 verifier 通过；仍不包含 heap 峰值采样或 256 MiB 内存目标结论。
